# Plan 07-02: Remove System Theme Option and Darken Shared Overlays

**Phase:** 7 - Dark Theme Foundation  
**Status:** Ready  
**Requirements:** THEME-02, THEME-03

<objective>
Remove the visible system-theme option and make dashboard profile settings, date controls, locked overlays, and upgrade modals readable on the dark dashboard foundation.
</objective>

## Scope

In scope:
- Remove or disable the `Sistema` theme option from dashboard profile preferences.
- Default dashboard preferences to dark if the local preference state remains.
- Convert profile settings modal surfaces and controls to dark-safe styling.
- Convert `CalendarFilter`, `LockedOverlay`, and `UpgradePopup` to dark-safe colors and focus states.

Out of scope:
- Persisting theme preferences to the database.
- Adding a light/dark theme switcher with real app behavior.
- Changing plan names, pricing, or permission logic.

<tasks>

### 07-02-01. Remove visible system theme behavior from profile settings

**Type:** implementation  
**Files:** `components/dashboard/profile-settings.tsx`  
**Action:**
- Change theme preference state away from `"light" | "dark" | "system"` to supported explicit modes only, or remove the inactive theme selector if it is purely decorative.
- Remove the `Monitor`/`Sistema` option from the visible UI.
- If a light/dark preference selector remains, default it to dark and ensure it does not claim system behavior.
- Keep the rest of profile, farm, language, notification, users, and security behavior unchanged.

**Verify:**
- `rg -n "Sistema|system|Monitor" components/dashboard/profile-settings.tsx`
- `npm run build`

**Acceptance criteria:**
- Users cannot see or select a system theme mode.
- Profile settings still compiles and opens.

### 07-02-02. Convert profile settings modal to dark-safe surfaces

**Type:** implementation  
**Files:** `components/dashboard/profile-settings.tsx`  
**Action:**
- Update modal panel, sidebar, header, tabs, forms, labels, selects, toggles, danger zone, and close/save buttons for dark readability.
- Preserve layout width, tab structure, and form density.
- Keep focus states visible with brand accents.

**Verify:**
- Manual profile modal inspection on desktop and mobile-width viewport.
- `npm run build`

**Acceptance criteria:**
- Modal text, controls, tab states, and destructive states remain readable on the dark dashboard.
- No text overlaps or clipped buttons are introduced.

### 07-02-03. Darken shared date, lock, and upgrade surfaces

**Type:** implementation  
**Files:** `components/date-filter/calendar-filter.tsx`, `components/plan/locked-overlay.tsx`, `components/plan/upgrade-popup.tsx`  
**Action:**
- Convert the calendar trigger, popover, mode selector, day/month cells, hover states, and today action to dark-safe styles.
- Convert locked overlay scrim/icon/message styles so locked content is legible and clickable on dark cards.
- Convert upgrade popup body and actions to dark-safe styling while preserving plan content and CTA behavior.
- Keep amber upgrade accents and brand/status colors distinct.

**Verify:**
- Manual scan of date filter, locked premium dashboard insights, sidebar locked nav popup, and upgrade modal.
- `npm run build`

**Acceptance criteria:**
- Date filter and plan-gated surfaces are usable on the dark dashboard.
- Upgrade popup remains readable and does not depend on a white modal body.

</tasks>

## Threat Model

### Assets

- User trust in theme behavior.
- Accessibility of modal and popover controls.
- Upgrade/locked plan UX used by later permission phases.

### Threats

- **Medium: Decorative theme selector promises behavior that does not exist.** Mitigate by removing `Sistema` and avoiding unsupported system behavior.
- **Medium: Dark modal conversion breaks form inputs or focus states.** Mitigate by keeping structure unchanged and verifying all tabs.
- **Medium: Locked overlay hides too much information or becomes unreadable.** Mitigate by using dark scrim styles and direct manual inspection.
