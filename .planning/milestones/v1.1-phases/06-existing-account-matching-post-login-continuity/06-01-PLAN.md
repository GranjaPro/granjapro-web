# Plan 06-01: OAuth Account Reuse and Login Continuity

**Phase:** 6 - Existing Account Matching & Post-Login Continuity  
**Status:** Ready  
**Requirements:** AUTH-03, AUTH-04

## Goal

Harden and verify the Google OAuth callback path so Supabase same-email identity linking lands users in the existing account/farm context, while first-time and incomplete users continue through the existing dashboard/onboarding behavior.

## Scope

In scope:
- Preserve the existing Google OAuth entry points from Phase 5.
- Keep Supabase Auth responsible for same-email OAuth identity linking.
- Harden `/auth/callback` around safe `next` handling, session exchange, profile/farm lookup, and onboarding destination selection.
- Add focused tests or verification helpers for callback routing decisions where the current test setup allows.
- Document required live Supabase/Google verification for same-email account reuse.

Out of scope:
- Manual account-linking UI.
- Account settings for linked identities.
- Custom duplicate-account merge tooling.
- Additional OAuth providers.
- Broad auth rewrite or custom auth backend.

## Files To Change

- `app/auth/callback/route.ts`
- `components/auth/auth-provider.tsx`
- `app/(auth)/login/page.tsx`
- `app/(auth)/signup/page.tsx`
- `supabase/migrations/00001_initial_schema.sql`
- `supabase/schema.sql`
- Optional, if a test pattern exists or can be added without broad setup churn: callback/auth routing test files.

## Implementation Tasks

### 1. Confirm OAuth entry points stay provider-owned

- Inspect the Phase 5 `signInWithOAuth` calls and keep them on Supabase's standard Google OAuth path.
- Do not create or upsert `profiles` rows from the login/signup pages before OAuth redirect.
- Keep `redirectTo` pointed at `/auth/callback` so callback continuity remains centralized.
- If adding `next` support to either CTA, restrict it to existing dashboard-relative destinations only.

### 2. Harden callback destination handling

- Extract the callback destination decision into a small local helper in `app/auth/callback/route.ts` if it improves testability without over-abstracting.
- Validate `next` as an internal relative path before redirecting.
- Preserve the existing email-confirmation behavior that allows non-dashboard internal routes such as `/login`.
- For dashboard destinations, keep the farm/profile check before choosing the final route.

### 3. Preserve existing-account farm continuity

- After `exchangeCodeForSession`, fetch the authenticated user with `supabase.auth.getUser()`.
- Query `profiles` by `user.id` and read `farm_id`.
- If no `profile.farm_id` exists, query `farms.owner_id = user.id` as the existing fallback.
- If an owned farm exists but `profiles.farm_id` is empty, update the profile to that farm when a profile row exists, matching the client auth-provider backfill behavior.
- Redirect users with a farm to the sanitized dashboard `next` destination.
- Redirect users without a farm to `/dashboard/onboarding`.

### 4. Keep first-time Google onboarding intact

- For a newly created Google user, rely on the existing `handle_new_user` trigger to create `profiles`.
- Confirm the trigger can populate `full_name` from OAuth metadata or the email prefix.
- Do not require signup form fields for Google-created users.
- Ensure users with no farm still reach the existing onboarding flow rather than a separate Google-specific setup path.

### 5. Add focused verification coverage

- Add the narrowest viable test coverage for callback decision behavior.
- Cover at least:
  - Existing user/profile with `farm_id` redirects to `/dashboard`.
  - Existing user with owned farm but missing `profile.farm_id` redirects to `/dashboard` and backfills the profile when possible.
  - User without farm redirects to `/dashboard/onboarding`.
  - Non-dashboard internal `next` destinations still bypass farm checks.
  - External or malformed `next` values fall back to a safe internal destination.
- If the repo has no practical auth route test harness, document these as manual verification steps in the phase summary and keep code changes small.

### 6. Add live Supabase verification checklist

- Document the required live check for AUTH-03:
  - Create or identify an email/password account with a farm.
  - Use a Google account with the same verified email.
  - Complete Google sign-in.
  - Confirm the session `user.id` matches the existing profile owner and no duplicate app profile/farm context appears.
- Document the live check for AUTH-04:
  - Fully set-up user lands in the existing dashboard flow.
  - User without farm lands in the existing onboarding flow.

## Threat Model

### Assets

- User account identity and session cookies.
- Farm ownership and profile linkage.
- OAuth callback redirect destination.

### Threats

- **High: Open redirect through callback `next`.** Mitigate by accepting only internal relative destinations and falling back to `/dashboard`.
- **High: Duplicate account/profile context for same email.** Mitigate by relying on Supabase automatic identity linking and verifying callback user/profile continuity against `user.id`.
- **Medium: OAuth user bypasses onboarding.** Mitigate by keeping the callback farm/profile check and dashboard onboarding behavior aligned.
- **Medium: Profile backfill links the wrong farm.** Mitigate by only backfilling from `farms.owner_id = user.id`, never by email alone.

## Verification

### Automated checks

1. Run the narrow callback-routing tests if added.
2. Run `npm run build` to catch route/type regressions.

### Manual checks

1. Existing email/password user with farm signs in through same-email Google and reaches the existing dashboard account context.
2. Same-email Google sign-in does not create a duplicate app-visible profile/farm context.
3. First-time Google user with no farm reaches the existing onboarding flow.
4. Existing fully set-up Google user reaches the dashboard.
5. Email confirmation callback with `next=/login` still redirects to login.

## Risks

- Supabase automatic identity linking cannot be fully proven by local unit tests; it requires a live configured Supabase project and a verified Google email.
- If existing Supabase Auth settings allow ambiguous or unverified duplicate users, the app should document the operational fix rather than trying to merge accounts in client code.
- Adding broad auth abstractions would increase risk; keep callback changes local unless implementation reveals duplicated logic that is already established elsewhere.

## Done When

- AUTH-03 is satisfied by Supabase same-email identity linking plus app-level continuity verification.
- AUTH-04 is satisfied for both fully set-up and not-yet-set-up users.
- `/auth/callback` remains safe, internal-only for redirects, and compatible with email confirmation.
- Phase 6 has documented live verification steps for the provider-level behavior.
