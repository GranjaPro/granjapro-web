# Plan 05-01: Google Auth CTAs, Terms Gate, and Inline OAuth Feedback

**Phase:** 5 - Google Entry Points & Signup Terms Gate  
**Status:** Complete  
**Requirements:** AUTH-01, AUTH-02, SIGN-01

## Goal

Update the existing login and signup pages so Google auth uses page-specific CTA copy, respects the signup terms gate, locks competing auth actions while the OAuth redirect starts, and shows inline feedback if the Google handoff fails before leaving the page.

## Scope

In scope:
- Add page-specific Google CTA copy for login and signup.
- Gate Google signup on the existing terms checkbox only.
- Add Google-specific loading state and disable competing auth actions while redirect starts.
- Show inline Google-path error feedback near the CTA when `signInWithOAuth` fails locally.
- Preserve the existing `/auth/callback` OAuth destination and current auth-page layout.

Out of scope:
- Same-email account matching and duplicate-account handling.
- Post-login callback changes beyond preserving the current redirect target.
- Broad auth-page redesign or new auth abstractions shared across the app.
- Explicit canceled-auth messaging after the user returns from Google.

## Files To Change

- `app/(auth)/login/page.tsx`
- `app/(auth)/signup/page.tsx`

## Implementation Tasks

### 1. Split manual auth state from Google auth state on both pages

- Add a dedicated Google loading flag instead of reusing the manual submit loading state.
- Add a dedicated Google error message so manual credential errors and Google handoff errors do not overwrite each other.
- Clear stale Google errors before a new OAuth attempt.
- Ensure the Google loading state disables:
  - the Google CTA itself
  - the manual submit button
  - manual form inputs that could start a competing auth action while the redirect is being initiated

### 2. Update login Google CTA behavior

- Change login CTA copy to login-specific wording aligned with the phase context, such as `Entrar com Google`.
- On click, set Google loading state immediately, then call `supabase.auth.signInWithOAuth(...)` with the existing `/auth/callback` redirect target.
- Handle the returned `{ error }` result from Supabase and surface an inline error banner/message near the Google CTA if the handoff fails before navigation.
- Use Google-specific loading copy such as `Conectando com Google...`.

### 3. Enforce the signup Google terms gate

- Disable the signup Google CTA until `acceptedTerms` is true.
- Do not require `fullName`, `email`, or `password` to enable the Google CTA.
- Add short helper text near the Google CTA explaining that terms acceptance is required before continuing.
- Reuse the same disabled visual language already used by the main submit button as closely as the current component structure allows.

### 4. Update signup Google CTA behavior

- Change signup CTA copy to signup-specific wording aligned with the phase context, such as `Criar conta com Google`.
- When terms are accepted and the CTA is clicked, start Google loading state, disable competing auth actions, and call the existing OAuth flow.
- If Supabase returns an error before redirect, restore the page to an interactive state and show inline Google-path feedback near the CTA.
- Do not consume typed manual signup fields for the Google path, but keep those local state values intact if the redirect never happens.

### 5. Keep current layout and callback continuity intact

- Keep the existing auth-page order: manual form, `ou` divider, then Google CTA.
- Keep the CTA full-width and visually secondary to the primary submit button.
- Do not change `app/auth/callback/route.ts` in this plan unless implementation reveals a concrete redirect regression.

## Verification

### Manual checks

1. On `/login`, the Google CTA is visible below the divider with login-specific copy.
2. Clicking login Google CTA changes the label to Google-specific loading copy and disables other auth actions while the request is in flight.
3. If `signInWithOAuth` fails on `/login`, the page stays in place and shows inline Google-specific error feedback near the CTA.
4. On `/signup`, the Google CTA starts disabled until the terms checkbox is checked.
5. On `/signup`, checking the terms box immediately enables the Google CTA even if manual fields are empty.
6. On `/signup`, helper text near the Google CTA explains the terms requirement while the CTA is disabled.
7. Clicking signup Google CTA after accepting terms triggers Google-specific loading/disable behavior and preserves any typed manual field values unless the browser leaves the page.
8. Manual signup and login still work after the Google CTA changes.

### Regression checks

1. Existing `/auth/callback` flow still points authenticated users to the current post-login routing logic.
2. Existing auth page structure, divider, and link placement remain unchanged.

## Risks

- Supabase OAuth may return control to the browser too quickly to visibly show the loading state in some environments; this is acceptable as long as the state is set before awaiting the OAuth call.
- Shared use of one `error` slot for manual and Google auth would create confusing feedback; keep those paths isolated during implementation.
- Over-disabling signup inputs could accidentally block the terms checkbox itself; only disable controls that trigger competing auth actions.

## Done When

- AUTH-01 is satisfied on the login page.
- AUTH-02 is satisfied on the signup page.
- SIGN-01 is enforced through the Google signup CTA gate.
- The phase remains within the current auth UI structure and defers duplicate-account handling to Phase 6.
