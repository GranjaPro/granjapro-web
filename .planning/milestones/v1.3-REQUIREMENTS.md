# Milestone Requirements: v1.3 - Functional MVP & Integrations

## Vision
Deliver a fully functional, monetization-ready, and security-hardened MVP of GranjaPro by the end of July. Focus purely on database integrations, payment flow, water/health loops, specialized inventory control, RAG-based AI assistant, and user feedback mechanisms.

---

## 1. Stripe Payment Integration

### Goal
Implement a subscription-based payment wall using Stripe Checkout to allow users to upgrade/downgrade their tier.

### Requirements
- **Plan Selection Screen**: Update `/dashboard/select-plan` to call a Next.js API route to initiate Stripe Checkout.
- **Stripe Checkout Session**: Implement the `/api/checkout` API route to create Stripe checkout sessions for monthly plans ("Essencial", "Pro", "Premium").
- **Webhooks Integration**: Implement `/api/webhooks/stripe` to securely receive event notifications (e.g. `checkout.session.completed`, `customer.subscription.deleted`) and update the user's `plan` in the `profiles` table.
- **RLS/Route Protection**: Ensure plan-based locks are respected across routes and database operations.

---

## 2. Inventory Management (Database Integration & Re-architecture)

### Goal
Re-architect the inventory management module to move from a single generic table to specialized tables for physical locations, feed, vaccines, and packaging, while securing automated expense integration for stock losses.

### Requirements
- **DB Re-architecture**: Connect the interface to the newly created tables: `storage_locations` (physical structures), `feed_inventory` (feed batches), `vaccine_inventory` (vaccine/medication batches), `packaging_inventory` (cartons/cases batches), and `inventory_losses` (loss logging).
- **Physical Locations Management**: Support physical storage locations with name, capacity, unit (kg, doses, units), status (active, empty, maintenance), and custom notes. Calculate aggregate occupancy dynamically from related batches.
- **Safe Location Deletion**: Implement database trigger (`handle_storage_location_deletion`) to automatically redirect batches to a default `"Default/Other"` location upon a location's deletion.
- **Batch Forms & Properties**: Update inventory forms to support specialized fields: Storage Location, Batch Number, Feed Type / Vaccine Name / Packaging Type, Initial/Current Quantities, Unit Price, Expiration Date (mandatory for vaccines), and notes.
- **Stock Loss Logging**: Support registering stock losses (e.g. mold, expiration, physical damage, theft) with automatic database trigger (`handle_inventory_loss`) that:
  - Deducts the lost quantity from the current batch.
  - Automatically calculates and writes the loss financial value.
  - Automatically generates an expense transaction in `financial_transactions` under category "Inventory" linked to the loss record.

## 3. Tasks & Notifications System

### Goal
Provide database-backed checklists and automated alerts for farm activities.

### Requirements
- **Task Management**: Implement the `/dashboard/tasks` page with full database-backed CRUD (Option B schema update).
- **Today Checklist**: Integrate the dashboard checklist component with the database tasks instead of React state.
- **Dynamic Alerts**: Connect the alerts panel to the database `alerts` table and auto-trigger stock alerts or laying rate warning notifications.
- **Evaluation Triggers**: Periodically trigger a dynamic system alert/notification asking the user to evaluate the app after a defined active period.

## 4. Water Flow & Health History Details

### Goal
Implement real-time water tracking and connect mock details pages to the database.

### Requirements
- **Separate Feed & Water Pages**: Keep `/dashboard/racao` as "Gestão de Ração" and create a dedicated `/dashboard/agua` page named "Consumo de Água".
- **Water Consumption**: Create a dedicated `water_consumption` table with RLS. Save water quantity only from the water page, not from the feed modal, and show real database metrics in charts/KPIs for Pro/Premium users.
- **Flock Water Page**: Update `agua/page.tsx` under flock details to query actual `water_consumption` records for that flock.
- **Flock Health History**: Update `historico-sanitario/page.tsx` under flock details to display actual events loaded from `health_records` instead of hardcoded `mockEvents`.

## 5. Feedback Collection System

### Goal
Collect user experience ratings, bugs, and general feedback directly in the app.

### Requirements
- **Feedback Page**: Create `/dashboard/feedback` page ("Tell us about your experience") with star rating (1-5), category selector, and description.
- **Access Points**: Add link to the feedback page at the end of the sidebar navigation, and a button inside the Profile Settings modal.

## 6. KPI Goals & Target Ranges

### Goal
Define and display targets across all pages for performance and loss metrics.

### Requirements
- **Customizable Dashboard Goals**: Allow users to click on dashboard KPI cards to open a modal and set custom targets (persisted in `kpi_goals` table).
- **Built-in Quality & Loss Targets (Production)**: Display fixed reference ranges in the production detail views:
  - Cracked or broken eggs: 3% to 5% of total production.
  - Dirty eggs: 1% to 2% of total production.
  - Deformed or shell-less eggs: 1% to 1.5% of total production.
  - Internal abnormalities: Less than 0.5% of total production.
- **Built-in Feed Consumption Targets**: Reference range of 110g to 130g of feed per bird/day. Display visual alerts on deviations.
- **Built-in Stage-based Water Consumption Targets**: Target ranges based on bird age/development stage (55ml to 245ml per bird/day).

## 7. AI Assistant Integration (Gemini 1.5 Flash via RAG)

### Goal
Integrate an intelligent assistant that acts as a copilot for the farmer, powered by Gemini 1.5 Flash via a Retrieval-Augmented Generation (RAG) pipeline with access to the farm's full datasets.

### Requirements
- **API Endpoint**: Connect `/api/ai/route.ts` to the Gemini API using the Gemini 1.5 Flash model (using the Google AI Studio free tier).
- **RAG Contextual Feeding**: Systematically fetch and aggregate all active farm data for the current user's `farm_id` (including active barns/flocks, feed/water consumption metrics, health records, mortality logs, financial transactions, and tasks) and inject this structured farm snapshot into the prompt context for the LLM.
- **System Prompt Safeguards**: Enforce strict system instructions to keep the assistant focused on poultry farming advisory, data analysis, and action items, preventing off-topic queries.

---

## 8. Farm Assistant Component Production Wiring

### Goal
Replace the mocked Farm Assistant component behavior with real app behavior while reusing the AI/API and farm-data integration delivered by the RAG assistant work.

### Requirements
- **Component Contract Preservation**: Keep the current Farm Assistant UI contract intact unless the phase plan explicitly identifies a required adjustment.
- **Mock Removal**: Remove mock-only responses, static farm context, and hardcoded assistant behavior from the component path.
- **Real Data/API Integration**: Connect the component to the app's real AI/API flow and active farm context, reusing existing services and types wherever available.
- **User-facing Failure States**: Provide clear loading, empty, and error states when the assistant cannot produce a response.
- **Test Coverage**: Cover the component integration path with tests or focused verification so mocked behavior cannot silently return.

---

## 9. Flock Mortality Page Integration

### Goal
Connect the flock-specific mortality page to the Supabase database to enable real tracking instead of mocked static values.

### Requirements
- **Real Data Fetching**: Fetch active flock mortality records from the `mortality` table filtered by `flock_id` (`loteId`) and `farm_id`.
- **Dynamic Metrics and KPIs**: Calculate total deaths, mortality rate, weekly mortality, and monthly totals dynamically from database records.
- **Interactive Charts**: Render the weekly area chart and monthly bar chart using real data from the database.
- **Database Persistence**: Update the register/edit form and the delete confirmation flow to make live writes to the `mortality` table via the `mortality` services.
