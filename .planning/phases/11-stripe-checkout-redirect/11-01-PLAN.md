# Plan 11-01: Stripe Checkout Session Redirect

**Phase:** 11 - Stripe Checkout Redirect  
**Status:** Ready  
**Requirements:** STRIPE-01

<objective>
Replace direct plan activation with a Stripe-hosted subscription checkout redirect for Essencial, Pro, and Premium monthly plans.
</objective>

## Scope

In scope:
- Install and use the official `stripe` Node package.
- Add a typed checkout config helper that maps `PlanType` to monthly Stripe Price IDs from environment variables.
- Create `POST /api/checkout` to authenticate the user, validate the selected plan, create a Stripe Checkout Session, and return the hosted Checkout URL.
- Update `/dashboard/select-plan` so each plan button starts checkout instead of updating `profiles.plan` directly.
- Update `UpgradePopup` so Pro/Premium upgrades use checkout instead of updating `profiles.plan` directly.
- Add pending/success/cancel/error UI states that do not claim the plan is active before webhooks run.

Out of scope:
- `/api/webhooks/stripe` implementation.
- Updating `profiles.plan` from Stripe events.
- Persisting Stripe customer/subscription IDs.
- Changing plan-gated route rules beyond removing client-side bypasses.
- New billing portal, downgrade/cancel, annual plans, coupons, taxes, invoices, or metered billing.

<tasks>

### 11-01-01. Add Stripe dependency and typed checkout config

**Type:** implementation  
**Files:** `package.json`, `package-lock.json`, `lib/stripe/checkout-config.ts`  
**Action:**
- Install the official `stripe` package.
- Create `lib/stripe/checkout-config.ts` with:
  - A `CheckoutPlan` type derived from `PlanType`.
  - A `CHECKOUT_PRICE_ENV_BY_PLAN` mapping for `essencial`, `pro`, and `premium`.
  - A function that accepts a `PlanType` and returns the configured Price ID or throws a clear error if the env var is missing.
- Reuse `PLAN_TYPES`/`PlanType` from `lib/plans.ts`; do not duplicate plan literals beyond typed mappings.
- Do not use `any`.

**Verify:**
- `npm run build` passes.
- Source search shows all three monthly Price ID env names are present exactly once in config.

**Acceptance criteria:**
- Stripe is available to server code.
- Price ID lookup is centralized and type-safe.
- Missing env configuration produces a developer-actionable error without exposing secret values.

### 11-01-02. Implement authenticated checkout session route

**Type:** implementation  
**Files:** `app/api/checkout/route.ts`, `lib/stripe/checkout-config.ts`  
**Action:**
- Add `POST /api/checkout`.
- Read JSON body as `unknown`, validate that `plan` is one of `PLAN_TYPES`, and reject invalid input with 400.
- Use `createClient()` from `lib/supabase/server.ts` and `supabase.auth.getUser()` to require authentication; return 401 when no user exists.
- Create one Stripe client from `STRIPE_SECRET_KEY`; return 500 with a safe message if it is missing.
- Create a Checkout Session with:
  - `mode: "subscription"`
  - `line_items: [{ price, quantity: 1 }]`
  - `success_url` returning to `/dashboard/select-plan?checkout=success&session_id={CHECKOUT_SESSION_ID}`
  - `cancel_url` returning to `/dashboard/select-plan?checkout=cancelled`
  - `client_reference_id` set to the Supabase user ID
  - `customer_email` from `user.email` when available
  - `metadata` including `user_id` and `plan`
- Return `{ url: session.url }`; if Stripe returns no URL, return 502 with a safe message.
- Keep profile mutation out of this route.

**Verify:**
- `npm run build` passes.
- With missing Stripe env vars, POST returns a safe error.
- With mocked/test Stripe env vars, route reaches Stripe session creation and does not attempt to update Supabase profiles.

**Acceptance criteria:**
- Authenticated users can request checkout sessions for all three plan keys.
- Invalid plans and unauthenticated requests are rejected before contacting Stripe.
- The route stores enough metadata for Phase 12 webhooks to reconcile the subscription.

**Verify:**

## Threat Model

### Assets

- User plan integrity.
- Stripe secret key and Price IDs.
- Supabase authenticated user identity.
- Checkout reconciliation metadata for Phase 12.

### Threats

- **High: Client-side plan bypass.** Mitigate by removing direct `profiles.plan` updates from plan selection and upgrade surfaces.
- **High: Unauthorized checkout creation.** Mitigate by requiring `supabase.auth.getUser()` before creating a session.
- **Medium: Plan/Price mismatch.** Mitigate through a typed `PlanType` to env mapping and validated request body.
- **Medium: Secret exposure.** Mitigate by keeping `STRIPE_SECRET_KEY` server-only and returning generic errors.
- **Medium: Premature active-plan messaging.** Mitigate with success copy that says activation waits for Stripe confirmation/webhook processing.
